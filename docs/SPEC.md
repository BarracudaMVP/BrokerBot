# Спецификация: Telegram-бот гаранта сделок по билетам

## 1. Контекст

Есть Telegram-группа, где покупают и продают билеты на мероприятия. Чтобы стороны не обманули друг друга, сделки проводит **гарант**:

1. Покупатель переводит деньги гаранту.
2. Продавец отправляет билеты (обычно PDF) в групповой чат сделки.
3. Покупатель идёт на мероприятие.
4. После успешного прохода гарант переводит деньги продавцу за вычетом комиссии.
5. Покупатель (иногда и продавец) оставляет отзыв.

Бот автоматизирует учёт и контроль этого процесса: ведёт статусы сделок, логирует переписку, проверяет участников по скам-листу, ведёт рейтинг и отзывы, напоминает и эскалирует проблемы модераторам.

### Принципиальное решение: бот НЕ двигает деньги

Бот — **учётная система**. Деньги переводят люди (гарант) вручную, а бот фиксирует факты по нажатию кнопок («оплата получена», «выплачено», «возврат сделан»). Автоматический приём и выплата денег — вне скоупа (юридические вопросы, платёжная деятельность).

### Масштаб

20–50 сделок в день. Postgres с запасом.

## 2. Роли

| Роль | Права |
|---|---|
| **user** | Регистрация, участие в сделках как продавец или покупатель, отзывы, просмотр своего профиля и сделок. |
| **guarantor** | Всё, что user + создание сделок и ведение **своих** сделок (подтверждение оплаты, выплаты, возврата). Гарантов несколько. |
| **moderator** | Просмотр **всех** сделок, решение споров, управление скам-листом (добавление, удаление, рассмотрение оспариваний). |
| **admin** | Всё + назначение ролей, глобальные настройки, импорт скам-листа. |

Роль проверяется на каждом действии, в том числе на нажатиях inline-кнопок (кнопку видят все в группе, нажать может кто угодно).

## 3. Ограничения Telegram Bot API (важно для реализации)

- Бот **не может создавать группы**. Группу под сделку создаёт гарант вручную и добавляет бота.
- Бот должен быть **админом** группы сделки с правами: приглашать пользователей (invite links), банить, удалять сообщения. Также нужно **выключить privacy mode** через BotFather (`/setprivacy` → Disable), иначе бот не видит обычные сообщения (админы видят всё, но лучше выключить явно).
- Бот **не получает событий об удалении сообщений**. Поэтому каждое сообщение копируется в лог сразу при получении.
- Бот получает `edited_message` — правки логируются как новые версии.
- `user_id` автора сообщения бот видит **всегда**, независимо от настроек приватности пользователя.
- По `@username` получить `user_id` обычного пользователя через Bot API **нельзя**. Поэтому бот ведёт свою базу всех увиденных пользователей и историю их username.
- Пересланное сообщение от пользователя со скрытой пересылкой приходит без `user_id` (`forward_origin` типа `hidden_user`).
- Телефон бот получает только если пользователь сам поделится контактом (кнопка `request_contact`). Обязательно проверять `contact.user_id == from.id`, иначе можно прислать чужой контакт.
- `KeyboardButtonRequestUsers` (выбор пользователя из контактов/чатов, бот получает `user_id`) работает **только в личке с ботом**.
- Invite-ссылки с `creates_join_request = true`: бот получает `chat_join_request` и сам решает, одобрить или отклонить.

## 4. Регистрация

1. Пользователь пишет боту `/start` в личке.
2. Бот просит поделиться номером через кнопку `request_contact`.
3. Проверка `contact.user_id == from.id`. Если не совпадает — отказ.
4. Проверка `tg_id` и телефона по скам-листу. Если найдено — регистрация отклоняется, пользователь помечается как заблокированный, модераторам уходит уведомление.
5. Сохраняем пользователя (tg_id, username, имя, телефон, дата).

Без регистрации участвовать в сделках нельзя.

**Попутно всегда:** при любом апдейте от пользователя обновляем его username/имя в `users` (если он есть) и пишем новые username в `username_history`. Для незарегистрированных пользователей, которых бот видит в группах, тоже записываем `tg_id` + username в историю (пригодится для поиска скамеров).

## 5. Создание сделки

1. Гарант создаёт группу, добавляет бота админом.
2. Гарант пишет в группе `/deal`. Бот проверяет, что автор — guarantor (или выше), и что группа ещё не привязана к активной сделке.
3. Бот пошагово собирает параметры (отвечать может только этот гарант):
   - название мероприятия;
   - дата и время начала мероприятия (вводятся в часовом поясе из конфига, хранятся в UTC);
   - количество билетов;
   - сумма сделки (цена билетов);
   - процент комиссии (задаётся на каждую сделку; минимальная комиссия — позже, через настройки);
   - кто платит комиссию: покупатель (сверху) или продавец (удерживается из выплаты).
4. Бот рассчитывает и сохраняет: сколько платит покупатель, сколько получает продавец, размер комиссии.
5. Бот генерирует **две invite-ссылки с заявкой на вступление**: «для продавца» и «для покупателя». Гарант отправляет их людям.
6. При `chat_join_request` по ссылке роли бот проверяет: пользователь зарегистрирован, не в скам-листе, роль ещё не занята. Если всё ок — одобряет заявку, назначает роль в сделке, отзывает ссылку. Иначе — отклоняет и пишет в группу причину (без лишних подробностей о том, что именно совпало в скам-листе).
7. Когда оба вступили, бот публикует карточку сделки со всеми параметрами и кнопкой «Подтверждаю» для каждой стороны. Сделка стартует после подтверждения обоими.

Покупатель в сделке один. Билетов может быть несколько (один PDF с несколькими билетами или несколько PDF).

## 6. Жизненный цикл сделки

### Статусы

| Статус | Что происходит | Кто двигает дальше |
|---|---|---|
| `CREATED` | Гарант заполняет параметры. | Гарант завершает мастер. |
| `WAITING_MEMBERS` | Ссылки выданы, ждём вступления и подтверждения обеих сторон. | Обе стороны нажимают «Подтверждаю». |
| `WAITING_PAYMENT` | Покупатель переводит деньги гаранту (может прислать скрин оплаты в чат). Параллельно бот в личке спрашивает у продавца реквизиты для выплаты и сверяет их со скам-листом. | Гарант нажимает «Оплата получена». |
| `PAID` | Оплата зафиксирована. Сразу переходит дальше. | Автоматически. |
| `WAITING_TICKETS` | Продавец отправляет PDF в группу. Бот фиксирует каждый документ от продавца как билет и спрашивает «Это все билеты?». | Продавец нажимает «Все отправил», покупатель нажимает «Билеты получил». |
| `TICKETS_SENT` | Билеты у покупателя. | Автоматически → `WAITING_ENTRY`. |
| `WAITING_ENTRY` | Ждём мероприятия. В момент начала бот присылает покупателю кнопки «Прошёл» / «Не пустили». | Покупатель. |
| `ENTRY_OK` | Покупатель подтвердил проход. | Автоматически → `PAYOUT_PENDING`. |
| `PAYOUT_PENDING` | Гаранту отправляется заявка на выплату: сумма, реквизиты продавца. | Гарант нажимает «Выплачено». |
| `CLOSED` | Сделка завершена успешно. Начисляется рейтинг, рассылаются запросы на отзыв. | — |
| `DISPUTE` | Спор, решает модератор. | Модератор. |
| `REFUND_PENDING` | Модератор решил вернуть деньги покупателю (полностью или частично). | Гарант нажимает «Возврат сделан». |
| `RESOLVED` | Спор закрыт решением модератора. Начисляется/списывается рейтинг, рассылаются запросы на отзыв. | — |
| `CANCELLED` | Отмена до оплаты (вручную гарантом или по таймауту). | — |

### Переходы в `DISPUTE`

- Покупатель нажал «Не пустили» (бот просит приложить доказательства: фото, скрины, текст).
- **Через 12 часов после начала мероприятия** покупатель не нажал ни одной кнопки. Автоподтверждения **нет** — сделка уходит модератору.
- Любая сторона или гарант нажали «Открыть спор» на любом этапе после `PAID`.
- Реквизиты продавца совпали со скам-листом (сделка замораживается, модератор уведомлён).
- Продавец не прислал билеты за отведённое время после оплаты (таймаут настраивается).

### Решение спора модератором

Модератор видит всю информацию о сделке (параметры, лог статусов, файлы, ссылку на переписку в лог-канале, доказательства) и выбирает:

- **Выплатить продавцу** → `PAYOUT_PENDING`.
- **Вернуть покупателю** (полностью) → `REFUND_PENDING`.
- **Частично** (модератор вводит, сколько продавцу и сколько покупателю) → выплата + возврат.
- Плюс указывает **виновника**: продавец / покупатель / внешние обстоятельства (никто не виноват).
- Плюс опционально **«Внести в скам-лист»** виновника (при полном обмане, не внешние обстоятельства).
- Комментарий модератора обязателен.

### Отмена

До `PAID` сделку можно отменить:
- гарант вручную;
- по таймауту: стороны не вступили/не подтвердили или покупатель не оплатил за N часов (настраивается).

После `PAID` отмена только через спор.

### Ключевое правило реализации

Все переходы статусов проходят через **одну функцию** в `internal/domain`, которая:
1. проверяет, что переход из текущего статуса в целевой допустим (таблица переходов);
2. проверяет, что действие выполняет пользователь с правильной ролью (гарант этой сделки, сторона сделки, модератор);
3. выполняет переход в транзакции с блокировкой строки сделки (`SELECT ... FOR UPDATE`), чтобы двойное нажатие кнопки не создало двойной переход;
4. пишет запись в `deal_status_log`.

Нельзя нажать «Выплачено» по сделке, где проход не подтверждён и спор не решён.

## 7. Логирование переписки

- Каждое сообщение в группе сделки копируется в **лог-канал** (`copyMessage`) с заголовком: номер сделки, автор (имя, username, tg_id), время.
- Каждая правка (`edited_message`) копируется как новая версия с пометкой «изменено» и ссылкой на копию оригинала.
- Файлы (билеты, скрины оплат, доказательства) тоже копируются.
- Параллельно всё пишется в `message_log` в БД, чтобы админка показывала историю сделки без поиска по каналу.
- Удаление сообщений бот не видит — поэтому копирование строго при получении.
- **Доступ к лог-каналу только у админов и модераторов**: там лежат валидные билеты и персональные данные.

## 8. Скам-лист

### Типы записей

- `tg_id` — Telegram user ID (не username: его легко сменить).
- `phone` — номер телефона, нормализованный (только цифры, в международном формате).
- `card` — номер карты. Хранится как **хеш** (HMAC-SHA256 с секретом из конфига) + последние 4 цифры для отображения. Сверка — по хешу.

Позже можно добавить другие типы реквизитов (кошельки и т.п.).

### Как попадают в список

- После решения спора с флагом «внести в скам-лист» (источник `deal`).
- Модератор вручную:
  - ответом на сообщение в группе: `/scam <причина>` (берётся `user_id` автора сообщения);
  - через кнопку выбора пользователя (`KeyboardButtonRequestUsers`) в личке с ботом;
  - по username — поиск по `users` и `username_history` (работает только для тех, кого бот видел);
  - вводом телефона или номера карты текстом.
- Импорт существующего списка (источник `import`). Формат файла — уточнить (вероятно CSV: тип, значение, причина).

### Где проверяется

- При регистрации (tg_id, телефон).
- При вступлении в группу сделки.
- При вводе продавцом реквизитов для выплаты.
- Опционально (позже): номера карт/телефонов, упомянутые в сообщениях чата сделки → предупреждение гаранту.

### Оспаривание

Через модератора: пользователь пишет модератору (или боту — команда, создающая обращение, которое видят модераторы). Модератор может удалить запись. Удаление логируется (кто, когда, причина), запись помечается как снятая, а не удаляется физически.

## 9. Рейтинг

### Структура

- Раздельный рейтинг: **как продавец** и **как покупатель**.
- Общий рейтинг = сумма двух.
- В профиле показываем все три числа и количество сделок в каждой роли. Пример:
  `Рейтинг 14.2 (продавец 11.0 / 3 сделки, покупатель 3.2 / 2 сделки)`.

### Вес сделки

Зависит от суммы. Функция настраиваемая (в конфиге), два варианта:

- `sqrt` (по умолчанию): `вес = max(1, sqrt(сумма / база))`
- `linear`: `вес = max(1, сумма / база)`

`база` — настраиваемая (например 1000 в валюте сделки).

### Изменения

| Событие | Изменение |
|---|---|
| Успешная сделка (`CLOSED`) | `+вес` каждой стороне в её роли |
| Спор решён, виновник — сторона | `−K × вес` виновнику (K по умолчанию 5, настраиваемый); невиновной стороне `+вес` |
| Спор решён, внешние обстоятельства | `0` обоим |
| Полный обман | виновник в скам-лист (рейтинг уже не важен) |

Все изменения пишутся в `rating_changes`. Поля рейтинга в `users` — кеш, который всегда можно пересчитать из `rating_changes` (нужна команда/функция пересчёта — пригодится при смене формулы).

### Отрицательный рейтинг

Блокировка — только через скам-лист. Пользователь с отрицательным рейтингом не блокируется автоматически, но гарант видит предупреждение при вступлении такого пользователя в сделку. (Порог автоблокировки — открытый вопрос, см. раздел 15.)

## 10. Отзывы

- После `CLOSED` или `RESOLVED` бот в личке просит обе стороны оставить отзыв о второй стороне: оценка 1–5 + текст (текст опционален).
- Оставить отзыв может только участник сделки, **один на сделку** (уникальность по сделке и автору).
- Продавцы оставляют отзывы реже — запрос всё равно отправляется, но не настойчиво (одно напоминание максимум).
- Отзывы видны в профиле пользователя.
- Отзывы на рейтинг не влияют (рейтинг считается по исходам сделок), это отдельная информация.

## 11. Интерфейс

### Для пользователей (личка с ботом)

- `/start` — регистрация.
- `/profile` — свой рейтинг, количество сделок, отзывы.
- `/mydeals` — свои сделки (активные и завершённые).
- `/check` — проверить пользователя (по выбору пользователя, username), телефон или номер карты по скам-листу и посмотреть рейтинг.

### Для гаранта

- `/deal` в группе — создать сделку.
- Кнопки в карточке сделки на каждом этапе.
- `/mydeals` — свои сделки с фильтром по статусу.
- Уведомления в личку: оплата ожидает подтверждения, заявка на выплату, спор открыт.

### Для модератора и админа (сначала в боте, позже веб-панель)

- `/deals` — список всех сделок с фильтрами: статус, гарант, участник, дата.
- `/deal_<id>` — карточка сделки: параметры, участники, лог статусов, файлы, ссылка на переписку в лог-канале, спор.
- `/disputes` — открытые споры.
- `/user` — поиск пользователя (по выбору, tg_id, username, телефону): профиль, сделки, отзывы, история username, записи в скам-листе.
- `/scam`, `/unscam` — управление скам-листом.
- `/import_scam` — импорт (админ).
- `/role` — назначение ролей (админ).
- `/settings` — глобальные настройки (админ): таймауты, параметры рейтинга, мин. комиссия.

## 12. Схема БД (Postgres)

Деньги храним в **минимальных единицах** (копейки и т.п.) как `BIGINT`. Время — `TIMESTAMPTZ` в UTC.

### `users`
- `tg_id BIGINT PRIMARY KEY`
- `username TEXT NULL`
- `first_name TEXT`, `last_name TEXT NULL`
- `phone TEXT NULL` (нормализованный)
- `role TEXT NOT NULL DEFAULT 'user'` — user / guarantor / moderator / admin
- `is_registered BOOLEAN NOT NULL DEFAULT false`
- `is_blocked BOOLEAN NOT NULL DEFAULT false`
- `seller_rating NUMERIC NOT NULL DEFAULT 0`, `buyer_rating NUMERIC NOT NULL DEFAULT 0` — кеш
- `seller_deals INT NOT NULL DEFAULT 0`, `buyer_deals INT NOT NULL DEFAULT 0` — кеш
- `registered_at TIMESTAMPTZ NULL`, `created_at`, `updated_at`

### `username_history`
- `id BIGSERIAL PK`
- `tg_id BIGINT NOT NULL`
- `username TEXT NOT NULL`
- `first_seen_at TIMESTAMPTZ NOT NULL`
- уникальность `(tg_id, username)`, индекс по `lower(username)`

### `scam_entries`
- `id BIGSERIAL PK`
- `type TEXT NOT NULL` — tg_id / phone / card
- `value TEXT NOT NULL` — tg_id или нормализованный телефон или HMAC карты
- `display TEXT NULL` — для карты: `**** 1234`
- `reason TEXT NOT NULL`
- `deal_id BIGINT NULL REFERENCES deals`
- `source TEXT NOT NULL` — manual / import / deal
- `added_by BIGINT NULL`
- `created_at TIMESTAMPTZ`
- `removed_at TIMESTAMPTZ NULL`, `removed_by BIGINT NULL`, `remove_reason TEXT NULL`
- уникальный индекс `(type, value) WHERE removed_at IS NULL`

### `deals`
- `id BIGSERIAL PK`
- `chat_id BIGINT NOT NULL` — группа сделки; уникальный индекс по `chat_id` для активных сделок
- `guarantor_id BIGINT NOT NULL`
- `seller_id BIGINT NULL`, `buyer_id BIGINT NULL`
- `seller_confirmed BOOLEAN`, `buyer_confirmed BOOLEAN`
- `status TEXT NOT NULL`
- `event_name TEXT NOT NULL`
- `event_at TIMESTAMPTZ NOT NULL`
- `tickets_count INT NOT NULL`
- `currency TEXT NOT NULL`
- `amount BIGINT NOT NULL` — цена билетов
- `commission_pct NUMERIC(5,2) NOT NULL`
- `commission_payer TEXT NOT NULL` — buyer / seller
- `commission_amount BIGINT NOT NULL`
- `buyer_pays BIGINT NOT NULL`
- `seller_receives BIGINT NOT NULL`
- `payout_details TEXT NULL` — реквизиты продавца (для карты — полный номер нужен гаранту для перевода; хранить с ограничением доступа)
- `seller_invite_link TEXT NULL`, `buyer_invite_link TEXT NULL`
- `deadline_at TIMESTAMPTZ NULL` — дедлайн текущего этапа (для планировщика)
- `created_at`, `updated_at`, `closed_at TIMESTAMPTZ NULL`

### `deal_status_log`
- `id BIGSERIAL PK`
- `deal_id BIGINT NOT NULL`
- `from_status TEXT NULL`, `to_status TEXT NOT NULL`
- `actor_id BIGINT NULL` — NULL, если переход сделал планировщик

- `id BIGSERIAL PK`

- `file_id TEXT NOT NULL`, `file_unique_id TEXT NOT NULL`
- `file_name TEXT NULL`, `mime_type TEXT NULL`
- `uploaded_by BIGINT NOT NULL`
- `created_at`

### `message_log`
- `id BIGSERIAL PK`
- `chat_id BIGINT NOT NULL`, `message_id BIGINT NOT NULL`

- `deal_id BIGINT NULL`
- `user_id BIGINT NOT NULL`
- `text TEXT NULL`
- `file_id TEXT NULL`
- `log_message_id BIGINT NULL` — id копии в лог-канале
- `created_at`
- уникальность `(chat_id, message_id, version)`

### `disputes`
- `id BIGSERIAL PK`
- `deal_id BIGINT NOT NULL`
- `opened_by BIGINT NULL` — NULL, если открыл планировщик (12 часов)

- `status TEXT NOT NULL` — open / resolved
- `resolution TEXT NULL` — payout_seller / refund_buyer / partial
- `seller_amount BIGINT NULL`, `buyer_refund BIGINT NULL`

- `id BIGSERIAL PK`

### `rating_changes`
- `id BIGSERIAL PK`

### `settings`
- `key TEXT PK`, `value JSONB NOT NULL`, `updated_by BIGINT`, `updated_at`
- Таймауты, параметры рейтинга (функция веса, база, K), мин. комиссия и т.п.

### Состояние пошаговых диалогов
Состояние мастеров (регистрация, создание сделки, ввод реквизитов, решение спора) хранить в БД (таблица `conversation_state`: user_id, chat_id, flow, step, data JSONB, updated_at), а не в памяти — чтобы переживать перезапуск.

## 13. Стек и структура проекта

- **Go**
- Telegram: `github.com/go-telegram/bot`
- Postgres: `github.com/jackc/pgx/v5`
- Миграции: `github.com/pressly/goose/v3`
- Конфиг: переменные окружения
- Планировщик: горутина, раз в минуту выбирает из БД сделки с истёкшим `deadline_at` (и сделки в `WAITING_ENTRY` для уведомления о начале мероприятия и 12-часового таймаута) и выполняет действия через domain-функцию переходов. Никаких таймеров в памяти.

```
cmd/bot/main.go
internal/
  config/        конфиг из env
  db/            подключение, запросы (репозитории)
  domain/        сделка, статусы, таблица переходов, расчёт комиссии и рейтинга
  bot/
    handlers/    команды, callback-кнопки, документы, join requests, edited messages
    flows/       пошаговые диалоги (регистрация, создание сделки, реквизиты, спор)
    logger/      копирование сообщений в лог-канал
    keyboards/   построение клавиатур
    texts/       все тексты бота (русский)
  scheduler/     дедлайны и таймауты
  scam/          нормализация, хеширование, проверки, импорт
migrations/
docs/SPEC.md
```

### Конфиг (env)
- `BOT_TOKEN`
- `DATABASE_URL`
- `LOG_CHANNEL_ID`
- `ADMIN_IDS` — начальные админы (через запятую)
- `TIMEZONE` — часовой пояс для ввода/отображения дат мероприятий
- `CARD_HASH_SECRET` — секрет для HMAC номеров карт

## 14. План реализации

1. Каркас проекта, конфиг, подключение к БД, миграции, запуск бота.
2. Учёт всех увиденных пользователей + история username. Регистрация с контактом и проверкой по скам-листу.
3. Роли, команда назначения ролей.
4. Создание сделки в группе, мастер параметров, расчёт комиссии, invite-ссылки с join request, подтверждение сторонами.
5. Логирование сообщений и правок в лог-канал и `message_log`.
6. Domain: таблица переходов, функция перехода с проверкой ролей и блокировкой.
7. Этапы оплаты, реквизитов, билетов, прохода, выплаты.
8. Планировщик: таймауты, уведомление о начале мероприятия, эскалация через 12 часов.
9. Споры и их решение модератором, возвраты.
10. Рейтинг (с пересчётом) и отзывы.
11. Скам-лист: ручное добавление всеми способами, снятие, импорт, `/check`.
12. Админ-команды: списки сделок, карточки, поиск пользователей, настройки.
13. Позже: веб-панель.

## 15. Открытые вопросы / позже

- Создание сделки самим участником (заявка, которую берёт гарант) — в исходной идее было, пока не проработано.
- Минимальная комиссия.
- Порог отрицательного рейтинга для автоблокировки (сейчас — только предупреждение гаранту).
- Ограничения для новых аккаунтов (лимит суммы) — пока не нужно.
- Формат импорта скам-листа.
- Защита от продажи одного билета нескольким покупателям (хеш файла, чтение QR) — пока не нужно.
- Автоматический приём и выплата денег — вне скоупа.
- Веб-панель для модераторов.
- Перепродажа некоторых билетов запрещена организаторами (особенно именных), их могут аннулировать. Нужно определить в правилах, чья это вина в споре.
